# v1 acceptance criteria

> The definition of "done" for the first complete release `(constitution-vs-roadmap)`.
> Each criterion has a **stable ID** (`F-1`, `I-4`, …). Roadmap issues ladder up
> to these IDs; the maintenance routine reads this file each run to compute what
> is still missing from v1, and decides **how** to get there itself.
>
> This file holds the **criteria** (durable) and the **authoritative per-ID
> status markers**. The markers are the source of truth for where v1 stands;
> live status is computed on demand from them plus actual repo / CI / ledger
> reality. There is no pinned status issue — when a marker drifts from reality
> it is corrected by PR.

## Status markers

| Marker | Meaning |
|--------|---------|
| ☐ | not started |
| ◐ | in progress |
| ☑ | done & verified |
| ⏸ | blocked / parked on `needs-operator` |
| ⊘ | waived or intentionally dropped (with recorded reason) |

## The v1 milestone (north star)

`cargo build --release --workspace` produces the `pokeemerald-rs` binary, and it:
runs to the **title screen** → starts a **new game** → plays through the
**protagonist's room** → the **first NPC interaction** → the **first wild
encounter** (a full battle) → the **first trainer fight** → and **saves, exits,
and reloads** cleanly. Tests, clippy, and fmt are green; every dependency is
justified; and the Operator has played it end-to-end and signed off on feel
`(behavioral-fidelity)`.

---

**v1 ships when** every row is ☑ or a recorded ⊘, and `H-1` (the playtest) is
signed `(gated-by-default)`. Until then, `FINAL` stays `0` and all releases are
prereleases. **How** to reach each criterion is the routine's call, planned
through GitHub issues — not prescribed here `(constitution-vs-roadmap)`.
